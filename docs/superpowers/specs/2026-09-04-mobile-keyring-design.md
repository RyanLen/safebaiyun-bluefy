# SafeBaiyun Bluefy 移动钥匙夹设计

## 目标

把现有单门验证页改造成只面向手机的多门禁工具。用户打开页面后应立即看到已保存门禁，并能从对应卡片发起 Bluefy 解锁；配置、导入和导出不得干扰这条主路径。

## 产品约束

- 只支持用户有权操作的门禁。
- 运行环境为 iPhone 上支持 Web Bluetooth 的 Bluefy HTTPS 页面。
- 纯静态 GitHub Pages，不使用账号、后端、框架、UI 库、CDN 或第三方字体。
- 所有门禁参数只保存在当前浏览器的 `localStorage`；这是明文的同源存储，不承诺硬件级密钥保护。
- 页面和日志不得主动上传、持久化或展示完整 `PRODUCT_KEY`。
- 导出的 JSON 包含可用于解锁的密钥，界面必须明确提示只分享给获授权的人。
- 现有 DES 与 20 字节握手帧算法保持不变。

## 用户与主任务

主要用户是站在门口、单手操作、希望在两秒内找到正确门禁并发起开锁的人。首页唯一的一级动作是“开门”；页面管理和数据迁移都是二级任务。

## 技术方案

继续使用浏览器原生 HTML、CSS 与 JavaScript，但把现有单文件拆为职责清晰的静态资源：

- `index.html`：语义化页面骨架、首页、管理页、编辑页、导入导出与 BLE 状态层。
- `styles.css`：移动端设计令牌、布局、组件、状态和动效。
- `core.js`：无 DOM 的门禁数据模型、校验、JSON 编解码、合并策略、DES 与协议帧。
- `app.js`：页面状态、DOM 渲染、存储、剪贴板和 BLE 生命周期。

所有脚本使用传统 `defer` 脚本并挂载少量全局对象，避免更改已经在 Bluefy 真机验证过的 JavaScript 运行模型。

## 数据模型

本地存储键为 `safebaiyun.doors.v1`，内容为：

```json
{
  "version": 1,
  "doors": [
    {
      "id": "本地生成的稳定标识",
      "name": "东门",
      "mac": "AA:BB:CC:DD:EE:FF",
      "productKey": "0123456789ABCDEF",
      "bluetoothName": "BYXXXX"
    }
  ]
}
```

导出格式同样使用 `version: 1`，但移除内部 `id`。导入时严格校验四个字段并规范化格式；以规范化后的 `mac + bluetoothName` 作为同一门禁身份，匹配项更新，其他项追加。单次导入要么全部成功，要么不修改现有数据。

## 信息架构

### 钥匙首页

- 顶部显示“我的门禁”和门禁数量，不放营销文案。
- 门禁卡片按保存顺序排列；门名最大，蓝牙名称为辅助信息，MAC 只显示末两段。
- 每张卡片提供一个占据卡片下半部的“开门”按钮，触控高度至少 56px。
- 首次无配置时显示空状态和唯一主按钮“添加第一个门禁”。
- 底部固定双标签导航：“钥匙”和“管理”，兼容 iPhone 安全区。

### 管理页

- 展示紧凑的门禁列表，每项可编辑或删除。
- 顶部主按钮“新增门禁”。
- “配置迁移”区提供“复制 JSON”和“导入 JSON”。
- 删除使用明确的二次确认，不依赖滑动手势。

### 编辑页

- 全屏页面而非拥挤弹窗。
- 字段顺序：门禁名称、`MAC_NUM`、`bluetoothName`、`PRODUCT_KEY`。
- 保存前统一规范化和校验；错误贴近对应字段展示。
- 编辑时允许保留原密钥，密钥默认遮挡并可临时显示。

### BLE 状态层

- 点击开门后从底部升起，不离开门禁列表。
- 顺序显示：选择/恢复设备、连接服务、读取挑战、计算应答、写入。
- 成功、失败、取消都有明确状态；失败时提供“重试”和“查看诊断”。
- 优先使用 `navigator.bluetooth.getDevices()` 查找此前已授权且名称匹配的设备；不支持或未找到时退回带名称过滤的 `requestDevice()`。
- 只有目标门禁的参数进入本次会话；断开后清除运行时引用。

## 视觉契约

- 方向：高对比、克制的工业钥匙夹；哑光石墨背景、暖白文字、安全橙作为唯一操作色。
- 8px 间距体系，卡片圆角 18px，操作按钮圆角 14px；避免玻璃拟态、渐变大标题、统计仪表盘和装饰性图表。
- 门名使用系统圆体/无衬线粗体，参数使用等宽字体。
- 所有可点击目标至少 44×44px，正文不小于 14px。
- 动效仅用于页面切换、BLE 状态层和操作反馈，并遵循 `prefers-reduced-motion`。
- 桌面仅居中显示最大 520px 的手机画布，不为桌面重新编排。

## 状态与恢复

- 加载：本地配置读取期间显示轻量骨架；读取失败回退为空列表并展示恢复提示。
- 空状态：引导新增或导入。
- 表单错误：逐字段显示，不清空用户输入。
- 导入错误：指出 JSON 语法、版本或第几个门禁字段错误；不部分导入。
- 剪贴板失败：保留可手动选择的 JSON 文本。
- BLE 失败：保留错误摘要和脱敏日志；允许重试同一门禁。
- 成功：显示门名和“指令已写入”；不把 GATT 写入成功伪装成机械状态确认。

## 验收标准

1. 第一次打开显示空状态，可新增至少两个门禁。
2. 刷新后门禁仍存在，首页直接展示门禁卡片。
3. 点击任意门禁只使用该门禁的 MAC、蓝牙名称和密钥执行现有 BLE 协议。
4. 门禁可编辑、删除，错误输入不会写入存储。
5. 导出 JSON 可复制；在清空环境中导入后得到等价配置。
6. 重复导入按 `mac + bluetoothName` 更新而不制造重复项。
7. 页面覆盖空、加载、连接、成功、失败、导入错误和剪贴板失败状态。
8. 现有 DES 标准向量与参考握手帧测试继续通过。
9. 390×844 与 430×932 两种手机视口没有横向滚动、遮挡或不可触达按钮。
